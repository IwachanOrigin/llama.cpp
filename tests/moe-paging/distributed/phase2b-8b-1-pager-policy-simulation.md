# Phase 2B-8B-1 online Expert cache policy simulation

The tool replays successful single-context Stage TCP traces. It uses
only (tensor_source_id, expert_id) as the key. Source names identify the
layer and gate/up/down tensor. The observed events, byte counts, role
metrics and generated bytes must agree with the observed LRU run. Each
policy starts cold for each prompt and is continuous across prefill and
decode. Separate phase totals do not reset policy state.

## Trace ordering

CPU MUL_MAT_ID acquires and releases on worker 0. In
llama_expert_cache::acquire, the hit callback runs after pin/MRU update
and the miss callback runs after slot reservation, before dropping the
cache mutex for I/O. Both callback sites hold that mutex. Stage TCP
owns one model and one context per process and issues one request at a
time. It sets the phase before llama_decode and reads seen only after
llama_synchronize. No worker can update seen concurrently with another
callback or a Stage request-boundary read in this configuration. On a
successful serial trace, miss publication and subsequent accesses
preserve LRU order. Concurrent contexts can publish misses in a different
order from their reservations. A failed read also has different
semantics. Neither case is modeled here. No diagnostic C++ changes were
necessary.

## Policies

| Policy | Admission and eviction | Incremental management cost |
| --- | --- | --- |
| Global LRU | Admit every miss, evict least recently used. | Existing slots and links. |
| Equal layer LRU | Assign floor(slots/layers) to each configured layer, give leftover slots to lowest layer IDs. | 32 B per layer, rounded to 64 B. |
| Resident LFU | Admit on miss at frequency 1. Evict smallest count, oldest access breaks ties. Nonresident counts are discarded. Counts saturate at 255 and halve (floor 1) every max(16, 10 × slots) accesses. | One byte per slot and 64 B control. Python scans on full misses. |
| SLRU | Admit to probationary MRU. A probationary hit promotes to protected MRU, demoting a protected LRU on overflow. Evict probationary LRU on a full miss. Protected cap is 50%, 75%, or 90%, with at least one probationary slot. Probationary can borrow unfilled protected capacity. | One byte per slot and 64 B control, with existing links reused. |
| TinyLFU-inspired admission | Global LRU victim. Admit to a free slot, or replace only if the incoming estimated frequency strictly exceeds the victim's. A rejection still reads. | Four rows of byte counters plus 64 B control, and one reserved payload slot. |
| Window TinyLFU-inspired | Window LRU is 1%, 5%, 10%, or 20%, rounded down with at least one window slot if two or more slots fit. Admit every miss to Window. On overflow, compete its old LRU against Main LRU using the same strict comparison. One resident slot uses ordinary LRU. | Sketch, one byte per resident slot, 128 B control, and one conservative transfer slot. |

The frequency sketch has width next_power_of_two(max(16, 4 × slots)),
deterministic BLAKE2b indexing, saturating counters at 15, and a full
halving pass every max(16, 10 × slots) accesses. It includes observations
of nonresident keys, has bounded memory, and omits a doorkeeper. This is
an online approximation, with collisions and aging, rather than a
canonical TinyLFU implementation. SLRU and window list operations are
constant-time. The sketch uses four indices per access plus victim
lookups on competition and an amortized linear reset. The Python elapsed
time includes replay accounting; it cannot predict C++ overhead.

Use Prompt A to select one parameter per policy, minimizing total requested
bytes on Coordinator and Worker across the requested budgets. Ties prefer
the smaller parameter. Evaluate B, C and D using the same settings. The
evaluation traces are opened only after settings are fixed. No future
events or overall access counts are used in an eviction decision.

## Budget and metric definitions

The x86-64 layout uses a 64-byte-aligned maximum Expert payload and
80-byte slot records. Recover fixed provider/cache overhead from the
observed allocation, then apply the C++ formula to other budgets. The
slot estimate is checked against the source trace's budget and count.
Other ABIs require verifying the slot record layout. Prospective policy
metadata is an aligned packed C++ estimate; Python container overhead
is excluded. The reserved slot includes metadata and aligned payload,
and cannot contribute to resident hits. W-TinyLFU counts a dropped
window candidate as a resident eviction. TinyLFU counts a rejected
incoming access as a bypass. In both cases each miss counts as one
reader call and requests the full Expert slice.

One scratch slot suffices for this serial replay. A C++ provider would
need a pinned scratch lease until all CPU workers complete the operation.
With concurrent contexts it could serialize bypass readers, or reserve
additional scratch capacity for concurrent leases. The trace lacks pin
and completion events, so it does not predict waits, parallel hit rates,
physical SSD reads or tokens/sec.

## Reproduce on the two Intel PCs

Use the build/model setup and the Baseline, Worker, Coordinator and SSH
commands from [Phase 2B-8A](phase2b-8a-pager-capacity.md), with the
following substitutions on both PCs:

- Use a separate directory for each prompt, for example
  results/policies/A/64, results/policies/B/64, results/policies/C/64,
  and results/policies/D/64. Use the prompt text from the task in a
  separate UTF-8 user.txt for each, with no System message.
- Keep budget=64, ctx=256, batch=2, threads=2, mmap, greedy, max-new-tokens=64,
  and the 24/24 split. Add --expert-trace-limit 200000 to common for all
  three roles. Keep --perf-details and --perf-cache-state uncontrolled.
- After both cmp checks pass, collect the Worker .experts.jsonl,
  .metrics.json and log in the corresponding PC-A directory. Keep
  Coordinator .perf.csv to recover phases for the Worker. Keep traced
  runs separate from the ordinary timing benchmark.
- Record executable revision, model identity, and commands. Use auto
  for independent model identity verification where feasible. An
  explicit shared identity label alone does not establish file identity.

Run from the repository root:

~~~bash
python tests/moe-paging/distributed/test-pager-policies.py
python tests/moe-paging/distributed/simulate-pager-policies.py \
  --development results/policies/A/64 \
  --evaluation B results/policies/B/64 \
  --evaluation C results/policies/C/64 \
  --evaluation D results/policies/D/64 \
  --output results/policies/comparison.json
~~~

For a direct check of LRU with nonzero observed hits, collect an additional
768 MiB trace for Prompt A in its own directory and use --development
for that directory with --policies lru. Check RAM and commit on both
machines before the run. Model weights, allocation and file-cache
behavior can differ by role and host.

## Integrating a candidate in a later C++ experiment

Keep Global LRU as the comparison mode. Update the frequency estimate at
the same access point where current LRU decides hit or miss. Compare
only against the oldest eligible resident. Pinned, wait-protected, and
loading slots retain their current eviction protection. If no candidate
is eligible, the concurrent implementation needs its own explicit wait
or bypass rule. The serial replay contains no observations of this case.

A bypass still needs checked synchronous shard I/O, a budgeted scratch
lease, and release after the CPU worker barrier. Preserve generation and
error handling on the lease. Measure scratch waits and the effect of
contention separately, and keep the cache mutex out of shard I/O. An
implementation that changes sketch hashing, tie-breaking, or aging should
replay the locked evaluation inputs again before comparing its results
with these estimates. Compare generated bytes, request bytes and wall
time separately. Use the untraced 768 MiB LRU runs as a timing reference.

Layer statistics attribute each event, including an eviction counter
increment, to the requesting layer. The report does not attribute
evictions to the layer that owned the victim.

## Phase 2B-8B-1 findings

Four 64-token real-model traces per role were captured on an ARM64 Windows
host using the x86-64 UCRT64 executable in loopback. Baseline and
Coordinator token IDs and UTF-8 matched for every prompt. All 829,908
access outcomes matched observed LRU at 64 MiB. A separate 16-token run
at 768 MiB also matched at every event, including 3,727 Coordinator hits
and 3,638 Worker hits.

At 256 and 512 MiB, both admission variants consistently reduced reader
request bytes in both stages. Plain TinyLFU-inspired admission had
slightly lower aggregate reader bytes than the locked 1% window at both
capacities, without the extra lists. At 512 MiB it reached 75–98% of
768 MiB LRU's total hits across the eight Stage traces but still
requested more bytes and had a lower decode hit rate. At 768 MiB it
lost decode hits in every Stage trace despite better aggregate prefill
reuse, and lost overall on Prompt D. Use plain admission as the first
low-memory C++ candidate and preserve 768 MiB Global LRU as a performance
reference. These are serial hit and byte estimates. Spot experiments
with the C++ implementation must measure request time, cache mutex
contention and scratch wait before drawing a throughput conclusion.
