# RPC findings

The code paths below refer to the feature branch. Upstream master documentation provides context for the interface and its experimental security status. [Official RPC documentation](https://github.com/ggml-org/llama.cpp/blob/master/tools/rpc/README.md)

- `tools/rpc/rpc-server.cpp` selects devices and starts the server. `ggml_backend_rpc_add_server` connects, negotiates HELLO and enumerates devices. `ggml_backend_rpc_init` creates a backend for a device. The CPU-only build exposed one CPU.
- `ggml_backend_rpc_buffer_type_alloc_buffer` uses ALLOC_BUFFER, and buffer set/get operations use SET_TENSOR/GET_TENSOR. Server buffer handles are connection-side objects. `rpc_dispatcher::graph_compute` serializes the graph for GRAPH_COMPUTE. `rpc_server::deserialize_tensor` and `rpc_server::graph_compute` reconstruct and dispatch to the selected backend. Nonzero graph UID reuse is supported by GRAPH_RECOMPUTE and tracked per device. The probe uses standalone graphs with UID zero, so both calls transmitted the full graph. Scheduler split graphs receive UIDs in `ggml-backend.cpp`.
- `ggml_backend_rpc_device_supports_op` returns true without checking the underlying CPU. `ggml_backend_rpc_device_supports_buft` checks RPC endpoint/device buffer compatibility. Validate the actual graph.
- `llama_model_base::load_tensors` uses the active offload layer range and device proportions to choose buffers. `llama_kv_cache::llama_kv_cache` uses `model.dev_layer(il)` when KV offload is enabled. This supports placement of ordinary weights, graphs and KV in principle. Our probe executed whole tiny graphs remotely. It did not establish mixed CPU scheduling or placement of a full Transformer stage. `--rpc` and `--tensor-split` alone do not specify the proposed independent local GGUF stages.
- `ggml_backend_sched_pin_external_experts` pins supported external nodes to a local CPU backend. RPC `rpc_tensor` carries type, shape, strides, op, flags, sources, view and buffer/data tokens. It has no provider or Extra field. A transmitted flag cannot create a Worker-local provider, file handle, source map, cache or lease. The Worker would need local tensor registration before execution and a scheduler route that does not copy slices. Ordinary MUL_MAT_ID therefore provides evidence about the CPU math only. The special Tensor was evaluated by code inspection.
- The stopped-server probe exited 2 within an 8-second harness deadline. Post-handshake transport failures go through RPC_STATUS_ASSERT in `rpc_dispatcher::work`. Server graph execution also asserts success. No established-session disconnect or recovery run was performed.

## Observed loopback run

Windows 11 ARM64 Snapdragon X Elite, x86-64 UCRT64 GCC 16.2.0 under emulation. Both operations ran twice on each CPU backend. MUL_MAT produced [8,18] and MUL_MAT_ID [28,38], exact FP32 bytes. Remote allocations were 96 and 128 B respectively. GGML RPC negotiated TCP version 10.0.0 on 127.0.0.1:50052.

The per-command log recorded 24 dispatcher commands after HELLO. This includes five SET_TENSOR, four GRAPH_COMPUTE and four GET_TENSOR. Application payload was 48 B of weights plus 20 B of activations/ID sent, and 32 B of results received. Full graph request bodies were 916 B per ordinary run and 1,212 B per indexed run, totaling 4,256 B. GET_TENSOR request bodies totaled 1,248 B. These are selected message bodies and tensor payloads. They exclude all TCP/link headers and do not add up to full socket traffic. The SET_TENSOR log prints its descriptor part separately from tensor bytes.

Summing the level-3 TCP send/receive trace and resolving its rounded KiB values with the packed definitions gives 13,930 B sent and 256 B received, including HELLO and RPC framing. Of those, 13,862 B sent and 224 B received are RPC metadata, commands and framing after subtracting tensor payloads. A general byte-counter implementation could account for commands, framing and payloads in `send_rpc_cmd_payload` and `send_rpc_cmd` including successful responses and HELLO, and report by command. For TCP/IP framing and retransmits use a loopback packet capture. The dispatcher log is sufficient for command mix and graph-body size in this probe.
